# 第5章: 差分テスト ― TS と Lean の整合性を担保する

- Lean オラクル: [`lean/Main.lean`](../lean/Main.lean)
- TS 側: [`difftest/oracle.ts`](../difftest/oracle.ts)（オラクルとの通信）, [`difftest/targets.ts`](../difftest/targets.ts)（比較の本体）, [`difftest/difftest.ts`](../difftest/difftest.ts)（CLI）
- バグ入り実装: [`difftest/buggy.ts`](../difftest/buggy.ts)

## 1. 問題: 証明したのは Lean 版だけ

第1〜4章では、Lean で書いたモデルについて定理を証明しました。
でも本番で動くのは TS のコードです。**TS のコードが Lean のモデルと同じ動きをする保証は、どこにもありません。**
写し間違い、TS 特有の挙動、後からの修正… ズレる原因はいくらでもあります。

## 2. 解決策: Lean のモデルを「正解」として実行する

Lean の定義は証明の対象であると同時に、**実行できるプログラム** でもあります。そこで:

```
               fast-check がランダム入力を生成
                          │
           ┌──────────────┴──────────────┐
           ▼                             ▼
   TS 実装（本番コード）        Lean モデル（証明済み）
   ts/ch3_sort.ts                Ch3.isort
           │                             │
           └──────────► 比較 ◄───────────┘
                    不一致 = TS のバグ
```

Lean のモデルは「整列済み ∧ 並べ替え」であることが**証明済み**なので、出力が食い違ったら、まず疑うべきは TS 側です。
ただし原因が必ず TS にあるとは限りません。JSON の読み書きや 32bit 値への変換など、`lean/Main.lean` の「つなぎ」の部分は証明されていないからです（第7節）。
このように正解を返す役のことを **オラクル（神託）** と呼びます。

> 実例: AWS の認可言語 **Cedar** は、仕様を Lean で書いて証明し、本番の Rust 実装と差分テストで突き合わせています。
> これにより、実装と仕様のズレがリリース前にいくつも見つかったと報告されています。

## 3. 仕組み

### Lean 側: JSON で話すオラクル

`lean/Main.lean` は標準入力から1行ずつ JSON を読み、Lean の関数で計算して返します。

```
$ echo '{"fn":"sort","args":[[3,-1,2]]}' | lean/.lake/build/bin/oracle
{"ok":[-1,2,3]}
```

```lean
  | "sort" => return toJson (Ch3.isort (← arg (α := Array Int) args 0).toList)
```

**証明した関数そのもの**（`Ch3.isort`）を呼んでいる点が重要です。別に書き直したコードでは意味がありません。

### TS 側: fast-check で比較

```ts
fc.asyncProperty(t.arb, async (args) => {
  const res = await oracle.query({ fn: t.name, args });
  return isDeepStrictEqual(t.impl(...args), res.ok);
})
```

fast-check は「プロパティベーステスト」のライブラリです。ランダムな入力を大量に作り、性質（ここでは「TS と Lean の出力が一致する」）が崩れる入力を探します。
崩れる入力が見つかると、それを **自動で小さく（縮小, shrinking）** してくれます。数学的に最小とは限りませんが、「これ以上どこを削っても再現しなくなる」所まで縮めます。

## 4. 動かしてみる

```
$ npm run difftest
  ✔ sum       1000 ケースすべて一致
  ✔ reverse   1000 ケースすべて一致
  ✔ sort      1000 ケースすべて一致
  ✔ midNaive  1000 ケースすべて一致
  ✔ midSafe   1000 ケースすべて一致
```

次に、ソートの `j >= 0` を `j > 0` と1文字だけ書き間違えたバグ版（`difftest/buggy.ts`）に差し替えます。

```
$ npm run difftest:buggy
  ✘ sort      不一致を発見（1 ケース目、縮小済み）
      入力: [[0,-1]]
      TS  : [0,-1]
      Lean: [-1,0]   ← Lean モデル
```

ランダムに見つかった配列が、最終的に **2要素 `[0, -1]`** まで縮められています。デバッグの出発点として理想的です。
（入力はランダムなので、実行のたびに `[[1,0]]` など別の2要素の反例になることもあります。再現性が必要なら `fc.check` に `seed` を指定します）
（`ts/ch3_sort.test.ts` のテストでもこのバグは見つかりますが、差分テストは「どんなテストケースを書くべきか」を人間が考えなくて済むのが強みです）

## 5. 入力の範囲 = モデルが保証する範囲

`difftest/targets.ts` では、入力の生成範囲を意図的に絞っています。

```ts
// TS の number は負数・小数・2^53 超を持つが、Lean の Nat にはない → 0..10000 の整数に限定
{ name: "sum", arb: fc.tuple(fc.nat({ max: 10000 })), impl: sum },
```

`sum(-3)` や `sum(2.5)` を Lean に渡しても、`Nat` として解釈できないのでエラーになります。
上限を付けているのには実行上の理由もあります。Lean の `sumTo` は末尾再帰ではないので、`sum(100000000)` のような巨大な入力ではスタックが溢れてオラクルが落ちます（その場合 TS 側は「Lean オラクルが終了しました」というエラーで止まります）。**証明に使うモデルは分かりやすさ優先で書くので、実行効率は良くないことが多い** のです。
つまり **Lean の定理が保証しているのはこの範囲だけ** で、範囲外の入力に対する TS の挙動は、別の手段（入力のバリデーションなど）で守る必要があります。

32bit の中点計算では、バグが境界に潜みやすいので `INT32_MAX` 付近の値を多めに生成しています。

```ts
const int32NonNeg = fc.oneof(
  fc.integer({ min: 0, max: INT32_MAX }),
  fc.integer({ min: INT32_MAX - 1000, max: INT32_MAX }),
);
```

## 6. 実務での運用

- **CI に組み込む**: `npm run lean:build && npm run difftest` を毎回実行します。`difftest` は不一致があると終了コード 1 を返すので、そのまま CI の失敗になります
- **変更をセットにする**: TS 側のロジックを変えるプルリクエストでは、Lean モデル・定理・差分テストも合わせて更新します
- **ケース数を調整する**: プルリクエストでは 1000 件、夜間ジョブでは 100 万件、のように分けるのが一般的です
- **反例を回帰テストに残す**: 見つかった最小反例は、`ts/*.test.ts` に普通のテストとして追加します（第4章でやったこと）

## 7. 何が保証され、何が保証されないか

| 層 | 保証の強さ | 手段 |
|---|---|---|
| Lean モデルが仕様を満たす | **証明**（全入力） | 第1〜4章の定理 |
| TS 実装が Lean モデルと一致する | **テスト**（試した入力のみ） | 差分テスト |
| 生成範囲外の入力 | 保証なし | バリデーション・型・レビュー |
| `lean/Main.lean` のつなぎ（JSON 変換、`BitVec.ofInt`/`toInt`）と fast-check | 証明なし（レビューで担保） | ― |
| Lean のカーネル・コンパイラ・Node.js | 信頼する（TCB） | ― |

**TCB（Trusted Computing Base）** は「正しいと信じるしかない部分」のことです。
形式検証は保証をゼロから作るものではありません。**信じるしかない部分を、小さく、はっきりさせる** ための道具です。

### 差分テストは「モデルが現実に忠実か」も確かめている

第4章では「`Nat` で考えるとバグを見逃す」ことを見ました。では `BitVec 32` のモデルが TS の `| 0` や `>> 1` と本当に同じ意味なのか？
`midNaive` と `midSafe` の差分テストがその証拠になります。壊れている `midNaive` まで TS と Lean で一致する、ということは **Lean のモデルが TS の 32bit 演算の挙動（折り返しも含めて）を正しく写し取っている** ということです。
証明は「モデルが正しいか」を教えてくれませんが、差分テストはそこに光を当ててくれます。

差分テストは証明ほど強くありませんが、「仕様の正しさは証明で」「実装との一致は大量テストで」と役割分担することで、TS のような検証ツールの無い言語でも、形式検証の恩恵を現実的なコストで受けられます。
